## 3. Spec Gaps Requiring PO Decision

### DEF-S001: display_name Fallback Contradiction 🔴 Blocker

| Field | Detail |
|-------|--------|
| **Sources** | AC-001f vs API Spec §4.1 |
| **AC-001f says** | *"A subscriber event arrives with youtube_handle but no display_name... The record is created with display_name = youtube_handle (fallback)"* |
| **API Spec says** | `display_name` is **Required** — returns `VALIDATION_ERROR` if missing |
| **Conflict** | If API rejects empty display_name, AC-001f cannot pass. If API allows it, validation rule is wrong. |
| **Impact on Testing** | TC-006 expected result depends on this decision |

**PO Decision Needed:**

| Option | Behavior | API Spec Change |
|--------|----------|----------------|
| **A** | `display_name` is optional. Backend falls back to `youtube_handle` when empty. | Change validation to optional |
| **B** | `display_name` is required. Empty → 400 error. | Remove or rewrite AC-001f |

---

### DEF-S004: Rate Limiting Has No Acceptance Criteria ⚠️ Clarification

| Field | Detail |
|-------|--------|
| **Source** | API Spec §5 |
| **API Spec says** | Rate limiting: 100 req/min per IP (default), 200 req/min (webhook tier) |
| **AC gap** | No AC in 013 covers rate limiting behavior |
| **Impact** | No test case exists for 429 response, per-IP tracking, or webhook tier |

**PO Decision Needed:**

| Option | Action |
|--------|--------|
| **A** | Add ACs for rate limiting to 013 — QA will write test cases |
| **B** | Defer rate limiting verification to Phase 2 — QA notes as out of scope |

## 4. Spec Gaps — Dev-Facing (No PO Decision Needed)

> These findings are for Dev awareness. PO does not need to make a decision, but should be aware.

### DEF-S002: Pagination Limit Not Capped

| Field | Detail |
|-------|--------|
| **Source** | API Spec §4.3 |
| **Gap** | `limit` parameter says "max 100" but no validation rule or error response for `limit=500` |
| **Recommendation** | Dev to add: clamp to 100 or return 400 for `limit > 100` |
| **Severity** | ⚪ Low |

### DEF-S003: Viewer Points Trigger Double-Count Risk

| Field | Detail |
|-------|--------|
| **Source** | DB Schema §5.2 (`sync_viewer_points()` trigger) |
| **Gap** | If a donation is updated `pending → matched → manual_review → matched`, trigger fires twice, double-counting points |
| **Recommendation** | Dev to add guard: only add points when `OLD.match_status != 'matched' AND NEW.match_status = 'matched'` |
| **Severity** | 🟡 High |

### DEF-S006: Webhook 401 Response — EasyDonate Retry Behavior

| Field | Detail |
|-------|--------|
| **Source** | API Spec §4.4 |
| **Gap** | If EasyDonate retries on 4xx responses, returning 401 for invalid signature could cause infinite retries |
| **Recommendation** | Dev to verify EasyDonate retry policy. Consider returning 200 with `{"skipped": true}` for invalid signatures |
| **Severity** | ⚪ Low |
